# ブラウザでの回答保存・復旧検証

## 実行

依存導入後にChromiumを入れる。

```powershell
./scripts/npm-local.ps1 ci
node node_modules/playwright/cli.js install chromium
# PowerShell 7で実行。このホストのWindows PowerShell 5はスクリプト実行が制限されている。
./scripts/test-db-local.ps1 -Suite e2e
# npmから呼ぶ場合もPowerShell 7を使用する。
./scripts/npm-local.ps1 run test:e2e:local
```

既に隔離されたlocalhost PostgreSQLを用意している環境では、`STUDY_GRAPH_ISOLATED_DB=1` と `STUDY_GRAPH_TEST_DATABASE_URL`（localhostの`/postgres`）を設定して `npm run test:e2e`。ホスト上に`psql`が必要。リモートDBと`postgres`以外の管理DB、URLクエリは拒否する。

## 何を通して検証するか

ブラウザ → 実際のNext.js画面/API → HTTPからSQLへのテスト用接続部分 → 23 migration（既存22 + 読取RPC）のPostgreSQL関数 → DB保存 → サーバーの受領結果 → ブラウザの次回日時。

- Notionの教材だけを固定データに置き換え、通常の復習では各科目の現在の問題を1問使う（あ／タレスの水／クロムレック）。単元では3科目19問の全Scope subjectと講義Relationを固定する。新規出題と初回受理の学習範囲確認もアプリ本体の処理を通す。
- DBの採点結果・復習予定・受領結果は模擬値を返さず、実際のSQL関数とサーバー採点を使う。テスト用接続部分は関数の引数型・権限を使ってSQLを呼ぶ。
- `.env.local`などの環境ファイルをコピーしない。子アプリとブラウザにはOSの必要変数と架空のテスト資格情報だけを渡す。
- Next.jsは使い捨てのソースコピーと別ポートで起動する。既存の3000番サーバーや`.next`に干渉しない。
- 子アプリのfetchは固定Notion・テスト用DB接続・子アプリ以外を拒否。ブラウザも子アプリ以外のHTTPアクセスを拒否する。
- 成否にかかわらず子アプリを停止し、作成したテストDBを削除する。PowerShell wrapperが専用PostgreSQLを停止する。成功時はクラスタを削除、失敗時は停止したクラスタを調査用に残す。
- `.tools/e2e-workspaces`に画面・アプリログを保持する。Gitには含めない。CIは画面とログのみ7日保持し、ブラウザprofileや環境ファイルをuploadしない。

これはhosted Supabase/PostgRESTの接続検証を代替しない。実サービスのHTTPゲートウェイ・資格情報・Notionの教材、実機Safari、通信なしでの起動、全教材内容は別途確認する。

## 37シナリオ（既存24＋単元13）

| 検証 | ケース数 | 完了条件 |
| --- | --- | --- |
| 通常の回答・自己評価 | 3科目 × 390px/820px = 6 | 正解、保存完了、DBの次回日時と画面が一致、横方向にあふれない |
| 評価を二重クリック | 3 | 回答履歴1件、SRS更新1回 |
| POSTが送信前に失敗 | 3 | IndexedDBに回答が残る。ブラウザ終了・同じprofileで再起動後、同じ回答IDで保存される |
| サーバー受理後に応答消失 | 3 | DBは既に保存済み、端末では未同期。再起動後に受領結果を照合し、端末も保存済みに収束する |
| 今日・復習入口 | 390px/820px = 2 | 3科目の未学習数が実際の出題と一致。画面表示・prefetch後の全privateテーブル内容が一致 |
| DB予定/Notion範囲の取得失敗 | 2 | 3科目を取得不可と表示し、0問/全問未学習と推測しない |
| 保存後の将来期限と期限到来 | 3 | 将来は0問・次回日時、期限到来後は復習1問。リンクから実際に1問が発行される |
| 科目flag停止/global v2停止 | 2 | 出題準備中と表示し、停止した問題の開始リンクを出さない |
| 単元の全問回答と結果再表示 | 3科目 × 390px/820px = 6 | 6/7/6問を完走。説明の言い換えを誤答と確定せず、原文と自己評価をDBへ保存。既存の復習予定が完全一致。概要と前回結果の表示で発行・保存しない |
| 単元の通信失敗と再起動 | 3科目 × 送信前失敗/受理後消失 = 6 | 2問保存後に3問目の通信を遮断。同じprofileの再起動後は4問目から再開し、同じ回答IDで収束。元の要求を再送しても履歴が増えず、全問完了してSRSを作らない |
| 単元開始の一時失敗と再試行 | 1 | 503でエラーを表示し、学習テーブルに書き込まない。同じボタンから再試行すると開始できる |

復旧後は元の送信内容をもう一度APIに送り、履歴1件・SRS更新1回を確認する。通信失敗はブラウザの要求を遮断し、受理後消失は実APIが200を返すまで待ってから応答を遮断する。テストがアプリの再送関数を直接呼ぶことはない。

サービスワーカーはこの検証では無効。通信なしの起動は既存のオフラインpilotを別に検証する。固定snapshotは最小表示データ。入口の予定は実際のNotion fixtureとDBの読取を通す。講義を読むフローは検証範囲に含めない。

## 再現した不具合と修正

1. 美術史が通常セッションの再接続・再表示時のoutbox復旧対象から外れていた。3科目を同じ復旧対象にする。
2. 受理後の応答消失時、再起動後には期限前なので出題が0問となり、回答コンポーネントが表示されず復旧が始まらなかった。問題が0問の画面でも既存のforeground復旧コンポーネントを動かす。

既存の回答ID・採点・SQL・復習間隔は変更しない。実行結果は `DEVELOPMENT_PLAN.md` に記録する。

単元の自己評価ボタンはoutbox保存・送信完了の後に次問へ進む。DBの確認は画面遷移を待ってから行う。Objective v2の正確な保存理由はReceiptの `reason` と `objective_srs_applications` にあり、旧 `exercise_attempts.srs_reason` の互換用4分類と混同しない。
