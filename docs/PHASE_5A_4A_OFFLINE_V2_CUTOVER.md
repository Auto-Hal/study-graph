# Phase 5A-4a: atomic offline Objective v2 prefetch cutover

Migration `20260925120000_phase_5a_4a_atomic_offline_objective_v2.sql` is migration 22. It is additive to migrations 1–21 and must pass a separate hosted migration gate. The implementation PR does not apply it to hosted Study Graph or change Production configuration.

Phase 4E prefetch pinned `issuanceRequestId` and `deviceId`, but its device-local unanswered-instance reuse did not share the Phase 5A Objective opportunity lock and unique active slot with online Review. Two devices, or online and offline, could consequently own distinct SRS-bearing instances for the same learner, Objective and epoch. The new wrapper calls `study_graph_issue_objective_instance_v2` inside its own PostgreSQL transaction. The generic issuer remains the only scheduler: it decides unseen, due, not-due, active reuse and stale/expired replacement. A wrapper failure before mapping commit rolls back a newly created instance and opportunity. When reusing a previously committed opportunity, a mapping failure leaves that opportunity unchanged.

## Transaction and lock order

An existing request mapping is recovered first. Ownership, exact device and persisted Kuzushiji Objective attribution are checked; current flags, Scope snapshot, due state, archive candidate and media compatibility do not alter its identity. A missing request in recovery-only mode returns zero rows, distinct from an RPC error. A genuinely missing create request validates the candidate archive and Objective binding, then takes the exact generic Objective advisory lock, then a request-ID advisory lock. It re-reads the mapping, locks and validates the current server snapshot pointer, calls the generic scheduled issuer, validates the *selected persisted* instance/revision/release/presentation, pins or reuses an offline delivery envelope, and inserts the immutable request mapping. No mutable instance or mapping row is locked before the Objective lock.

The first offline mapping for an instance fixes its snapshot reference, assets and feedback. Further devices and request IDs mapped to that instance reuse the same envelope, preserving the existing IndexedDB instance identity; only request/device delivery metadata differs. An online-issued instance gets a new envelope without rewriting `instance.scope_evidence`. The snapshot is delivery evidence, never first-acceptance authority; fresh Notion Scope still runs on the first attempt. The browser sends only `deviceId` and `issuanceRequestId`. Descriptor version 1, the six-field attempt request hash, Receipt v2, IndexedDB, the outbox and service worker are unchanged.

## Immutable media compatibility

Historical revision v1 has a null asset checksum and remains valid, answerable immutable content. All *future new* online and offline Kuzushiji Objective issuance proposes the existing checksum-pinned revision v2 and release v2. A valid active v1 opportunity still wins over that candidate; online Review renders the persisted v1 instance. A new offline request against that active v1 instance fails with `offline_asset_integrity_unavailable` (HTTP 409) before envelope or request mapping insertion. It neither substitutes v2 nor creates a duplicate opportunity. A committed historical request mapping is still recovered exactly, including one pointing to a checksum-null, accepted or expired instance. Offline delivery of a newly selected instance requires the archived asset's valid SHA-256, presentation agreement, and the existing client verification of downloaded bytes. There is no checksum overlay or historical archive backfill.

## Compatibility and cutback

The old public `study_graph_prefetch_kuzushiji_objective_instance` stays available for recovery of committed requests only. A missing request fails with `offline_prefetch_v1_issuance_closed`; an old deployment cannot resume device-local issuance. Historical all-null scheduling-context instances still use historical acceptance; complete v2 context uses v2 acceptance, and partial context fails closed. Accepted no-SRS remains terminal. There is no legacy Review dual-write.

Disabling *new* offline issuance does not prevent request recovery or acceptance of already-issued v1/v2 instances. Operational cutback requires a deployment that retains this routing, the checksum-null 409 behavior, and revision v2 for future new issuance. A deployment that proposes new revision-v1 opportunities is not an approved rollback target. The schema need not be rolled back for operational cutback.

The wrapper is `SECURITY DEFINER` with `search_path=pg_catalog`, schema-qualified private references and explicit service-role-only `EXECUTE`; private tables retain RLS and no direct application grants. Isolated PostgreSQL tests use migrations 1–22 and real concurrent connections for online/offline and multi-device races. No hosted writer RPC is called during implementation.
