## Failure and lifecycle handling

On SQL failure, the explicit transaction rolls back. Keep cutback and stop; inspect migration history, both function definitions/ACL and protected data by read only. On connection loss, do not resend: determine commit status from the ledger and fingerprints. If uncertain or partially inconsistent, stop for a reviewed forward repair; never rerun migration 22, modify history, delete data, or roll back immutable rows. On deploy or verification failure keep both cutback flags false and inspect reads/logs. Do not switch back to old revision-v1 new issuance code.

If the original opportunity is still active and its binding unexpired, any later authorized canary may share exactly the existing instance after all preceding checks. If it expires, is terminal/accepted, changes epoch/revision/state, or another opportunity appears, stop the existing-instance canary before calling the wrapper.
